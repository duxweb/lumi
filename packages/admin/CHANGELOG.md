# @duxweb/lumi-admin

## 0.1.0

### Minor Changes

- `ListPage` has a `toolbar` slot between its header and the results, where a JSON page puts a `FilterBar`; the list's `filters` read the value the bar binds.
- A JSON page on a route with path params reads them from page state at `/route/params` (`/orders/:id` gives `/route/params/id`), as the `Include` and `Iframe` descriptions already said; opening another record starts the page over. A page's own `state.route` gives way to it.
- A colour mode chosen on the sign-in page of a protected manifest follows the reader into the app.
- Closing the open tab leaves its page first and removes the tab once the reader is on the next one, so choosing to keep editing unsaved changes keeps the tab.
- The router provider writes an array query value as a repeated key.
- `config.json` takes `packKey`, and `createAdmin({ packKey })`: the key of packed manifests, pages and themes when the backend masks them with one (see `/lumi`). Packed answers without a key need no setting.
- A drawer address containing a space or control character is refused: a URL parser trims or drops them, so `?drawer=%20https://…` or `/%09/host` used to pass the same-site check and load a page from another site.
- Manifest, page and theme requests reach the signed client only at this site and the API: an API root written as a path (`/api`) no longer makes every origin count as the API.
- Signing out or losing the session forgets every loaded page, drawers and included pages too, and the reader's open tabs, so the next reader in the same browser tab starts clean.
- Menu items follow the access of the nearest ancestor route when their own route sets none, so a child of a refused parent is no longer offered. `flattenAdminRoutes` entries carry that `access`.
- Links below a router basename route correctly whether written as the address (`/admin/users`) or the route (`/users`).
- A handler named like a built-in Admin action (`navigate`, `openDrawer`, `closeDrawer`) is refused by name when the Admin is created, instead of failing every page at render.
- With several panels each keeps its own shell storage (tabs, preferences, language) unless `shellStorageKey` is set; `basename` must be a path such as `/console`.
- A console warning says so when the manifest sets `access` on routes but there is no access provider (for example after an extension replaced the sign-in without `accessProviders`).
- `ListPage` shows its `state`; header actions translate `labelKey`; closing two unsaved drawer layers and keeping the lower one no longer lets the next navigation through unasked; a malformed address fragment (`#100%`) no longer breaks the shell. `matchesAdminPath`, which nothing used, is removed.
- Another site inside a page. A route's `page` may be `{ "iframe": "https://bi.example.com/sales" }`: the frame fills the page area, titled by the menu label, with menus, tabs and access as for any route; relative paths resolve against the manifest (or `config.json` for an inline one). `config.json` takes `frameOrigins` (https origins), and `createAdmin({ frameOrigins })`, limiting `page.iframe` routes and `Iframe` elements to those sites and this one.
- `adminMessages` is `adminTranslations`.
- `config.json` renames `i18n.messages` to `i18n.translations`: the translations every page shares, per locale, inline or by URL. A page's own text goes in its `translations` (see `/lumi`).
- Pages written in JavaScript. A route's `page` may be `{ "module": "/pages/report.js" }`: an ES module loaded with native `import()` when the route first opens, once per URL (a failed load retries on the next visit), and rendered with the route's `params` and `query` (`AdminModulePageProps`). In the prebuilt base the module's default export receives the runtime and returns the page component, like an extension module; `createAdmin({ loadPageModule })` decides for compiled hosts, `import()` and the default export by default. Modules are static public files: never sent through `pages`, and only a manifest route can name one — drawer `src` and `Include` open JSON pages only. An inline manifest's `module` paths resolve against `config.json`, and its page `src` values stay as written when the panel has `pages`, so they reach the endpoint as the `path` the backend expects.
- `Include` shows another JSON page in place of an element, for a block several pages share. `src` is written like a route's `page.src` (and goes through `pages` when the panel has it); the page loads when first shown and is cached by `src`. Its state is its own, with `params` at `/include/params`; bound params that change start it afresh. A page that includes itself, directly or further down, or includes nested deeper than `MAX_INCLUDE_DEPTH` (8), shows an error in place. React hosts get `AdminInclude` and `AdminIncludeProvider`.
- Pages served by the backend. A panel (or `createAdmin`) takes `pages: { endpoint, method, data }`: every page `src` that is not a full URL — route pages and drawer pages alike — is sent as `path`, with `data` beside it, to `endpoint` through the default data provider, so it is signed, refreshed and unwrapped like any other request. `method` is `POST` by default; `GET` sends the values as the query. Each page still loads once and is cached by its `src`; a page the backend refuses shows as failed to load; a full URL is still fetched directly. The manifest, extension modules and images are not proxied.
- Shared drawers and modals from any JSON page. `openDrawer` takes `src` (a site or manifest-relative page address) as well as a registered `name`, with `id`, `params`, `title`, `mode` (`drawer` or `modal`) and `size`. The document loads and caches by its address alone; `id` and `params` reach it as page state at `/drawer/id` and `/drawer/params`. Opening from inside a drawer stacks a layer on top (three at most, deeper replaces the top); `closeDrawer` and a layer's close button close that layer and those above it, each layer asking about its own unsaved changes. The address carries every layer (`drawer`, `record`, `drawerParams`, `drawerTitle`, `drawerMode`, `drawerSize`, repeated per layer), so a shared link or a refresh reopens the stack; an address on another site is ignored. `useAdminDrawer()` exposes `layers` and `open(target, { id, params, title, mode, size })`; `readDrawerLayers`, `writeDrawerLayers` and `isDrawerPageSource` are exported. The unsaved-changes scope `routed-drawer` becomes `routed-drawer:<layer>`.
- One config shape for one back office or several. `config.json` loses `api`: `data`, `auth`, `access` and `panels` sit at the root, each one object (named `default`) or a list of items told apart by `name`. `data` items are backends (`url`, `live`, `auth: false`, the old `api.url` and `api.sources`); `auth` items are sign-ins (`mode`, `tokenKey`, `csrf`, `data`, and the endpoints under `endpoints`); `access` items are permission rules; `panels` are the back offices, each with its `path`, `manifest`, `manifestAuth`, `theme`, `login`, `auditLog`, `menuBadges`, `shellStorageKey` and the names of the `data`, `auth` and `access` it uses. One page serves every panel: the address picks the panel whose path holds it (the longest wins), any other address opens `defaultPanel` (else the first) at its own path; a page of its own names one with `data-panel` on the base script or `mountAdmin(config, extensions, { panel })`. Each panel has its own session and cache, a token key per auth name unless `tokenKey` is set, and panels naming the same auth share a sign-in. `selectAdminPanel` and `adminConfigItems` (in `/catalog`) expose the choice. Extensions get `{ config, panel, http }`, and replace providers by name with `authProviders` and `accessProviders` instead of `authProvider` and `accessProvider`; `dataProviders.default` is the mounted panel's backend. `MountedAdmin` adds `panel`. `resolveAdminBaseConfig` also takes a function of the loaded JSON, for a host that fills in part of a panel.
- An extension's `dataProviders` entry may give only `{ onRequest, onResponse }`: the provider the config builds for that name keeps its address and gains the hooks. On `default` (the mounted panel's backend) they reach every request to it — data, sign-in, uploads, the agent, the event stream and served menus and pages; another backend gets only hooks named for it, and hooks for a name `data` lacks fail the mount.
- Extension modules define their actions. `AdminExtension.actions` maps a handler name to `{ params, description }` (zod params), so a page that calls the action is validated like one calling a built-in action, and authoring tools describe it. Every name in `handlers` joins the catalog; a handler without a definition is still accepted, with its params unchecked.
- Menus and pages a backend serves per reader: the manifest, page and theme loaders send requests to the page's own origin or the API's through the app's signed client (credentials, locale, tenant, one refresh on a 401); other origins get a plain fetch, so a token never reaches a CDN.
- Permission strings in the backend's own shape. `createSimpleAuthProvider({ permission: { separator, format } })` builds the string a `{ resource, action }` check looks for: `system/users` + `delete` is `system:users:delete` by default (each `/` of the resource becomes the separator), `system.users.delete` with `separator: '.'`, and `format` reorders it, e.g. `{action}{separator}{resource}`. Every granted segment may be `*` and a trailing `*` covers everything below, so `system:*`, `*:users:delete`, `*` and the existing `orders:*` and `*:*` all work. A nested resource's permission is now `shop:orders:delete` rather than `shop/orders:delete`. `createPermissionMatcher` exposes the same rule for custom access providers.
- Table rows carry their own buttons. `Table`, Admin `DataGrid` and `ListPage` take a `rowActions` slot: its elements (plain `Button`, `Popconfirm`, …) are drawn in every row of the `kind: "actions"` column, each with its own `on`, so Edit can `setState` a dialog open while Delete runs `delete` behind a confirmation. Props read the row through native `$item` and `$index`; before a control's action runs the row is written to the bound `activeRow`, so params read it with `{ "$state": "/table/row/id" }` (native `$item` in action params is a state path, not a value). A click on a control does not also fire `rowClick`. Without the slot, the column's `actions` menu and `rowAction` work as before. React hosts pass `renderRowActions(row, index)` to `LumiTable`; `rowActionsRenderer` builds it from slot children inside a native repeat scope.
- The demo adds “CRUD”, the CRUD guide's JSON page, and its mock refuses a duplicate customer name with a field error.
- One request path, with the credentials owned by the auth provider. `createHttpClient` (in `@duxweb/lumi`) sends every request: it asks the `AuthProvider` for the request's credentials through the new optional `authorizeRequest({ url, method })`, which returns headers and/or fetch `credentials`, so a bearer token, an API key, a signature or a cookie session with a CSRF header are all written once, in the provider that keeps them. It adds `Accept-Language` and the tenant header, encodes JSON, and on a 401 calls the provider's new optional `refresh()` once (shared by concurrent requests) before sending again; a non-2xx answer becomes a `DataProviderError`. Headers a request names itself never override the auth's. `http.extend({ baseUrl, auth: false, headers })` reaches another backend without the app's credentials, and a 401 from such a client does not sign the reader out.

  `createSimpleDataProvider` takes `http` instead of `getToken`, `tokenHeader`, `getLocale`, `getTenant` and `fetcher`, and exposes it as `DataProvider.http`; uploads, the agent and `createSseLiveProvider({ http })` sign through the same client, so `upload.headers` and `agent.headers` are only for extra headers and `agent.credentials` is gone. `createLumi` takes and exposes `http` (built from `authProvider`, `i18nProvider` and `tenantProvider` when not given). `createSimpleAuthProvider` runs its own sign-in requests through an HttpClient (`http` option) and gains `mode: 'cookie'` with `csrf: { cookie, header }`, and `endpoints.refresh`; `SimpleAuth.getToken` is removed. `dataProviderAuth`, `withSourceAuth` and `DataProviderAuth` are removed.

  In Admin, an `auth` entry takes `mode`, `csrf` and `endpoints.refresh`, and each `data` entry takes `auth: false`. Extension options are flat: `authProviders`, `accessProviders`, `i18nProvider`, `tenantProvider`, `liveProvider`, `auditLogProvider`, `toastProvider`, `notificationProvider`, `validator`, `upload`, `agent` and `env` sit beside `dataProviders` instead of under `providers`, and a module's `dataProviders.default` replaces the panel's provider. Extension module functions receive `{ config, panel, http }`, `http` being the app's signed client at the panel's backend. `getToken` is removed from the extension options and from `MountedAdmin`, which exposes `http`. The demo mock answers cookie sessions as well.
- Menu items without a `group` or `module` share a default one whose label is translated (`lumi.admin.workspace`, 工作台 in Chinese) instead of always reading "Workspace".
- Account pages beyond sign-in. `AuthProvider` gains optional `register`, `forgotPassword` and `updatePassword`, with the `useRegister`, `useForgotPassword` and `useUpdatePassword` hooks; registering goes through the same session queue as `login`, so a provider that signs the new account in resets cached session data the same way. `createSimpleAuthProvider` offers each one only when its endpoint is set (`endpoints.register`, `forgotPassword`, `updatePassword`), and the base config takes them under an `auth` entry's `endpoints`.

  Admin adds `/register`, `/forgot-password` and `/reset-password` for an auth provider that implements the matching method, as `LumiAdminRegister`, `LumiAdminForgotPassword` and `LumiAdminResetPassword`. Sign-in links to them: "Create an account" (hidden with `login.register: false`) and "Forgot password?" opening the reset page instead of the administrator toast. The reset request never says whether an address has an account, and a reset link without its token asks for a new one.

  All four share `LumiAuthLayout`: the brand and display tools along the top with an optional help link, and beside the card the host's own copy: an optional badge, a headline with a phrase drawn in the brand colour, a description and a list of points (icon, title, one line), over a thin wash of the brand colour.
